# kream-reresell

KREAM 랭킹 상품(또는 검색 결과, SHOP 카테고리 목록)을 훑어서, 빠른배송 수요가 충분하고 마진이 나는 상품에
**일반배송(창고 보관) 구매 입찰**을 자동으로 넣고, 이미 넣은 입찰 중 기준에 못 미치게 된 것을 자동으로 지우며,
남에게 밀린 입찰의 희망가를 반복해서 올려 주는([재입찰]) 프로그램.

## 판단 규칙

1. 랭킹 탭 → 랭킹(기본 `가방`, 여러 개면 준 순서대로) → 순위대로 상품을 본다.
   랭킹은 랭킹 탭에 있는 21개 전부 고를 수 있다 (신발·러닝화·부츠 포함).
   **랭킹 대신 검색**으로 상품을 고를 수도 있고 (아래 "검색으로 상품 고르기"), **SHOP 탭의 카테고리 목록**으로 고를 수도 있다
   (아래 "SHOP 카테고리로 상품 고르기") - 그 뒤 2~8 은 똑같다.
   신발·러닝화·부츠·의류(아우터, 바람막이, 패딩, 상의, 하의 ...)처럼 **옵션(사이즈)이 있는 상품은 옵션마다 따로** 아래 2~8 을 적용한다
   (아래 "옵션이 있는 상품").
2. 상품 페이지 "거래 내역 더보기" 에서 **최근 30일 빠른배송(⚡) 체결 건수** 를 센다. 15건 미만이면 건너뛴다.
3. 구매하기 모달에서 **빠른배송 가격 = A** (내가 팔 예상가, 95점 가격은 무시).
4. 일반배송 → "즉시 구매 / 구매 입찰" → 구매 페이지의 **즉시 판매가 = B**.
5. `A - B > A × 최소 마진율` 일 때만 입찰. 최소 마진율은 **A 금액 구간별**로 다르게 둘 수 있다
   (예: A 0~50,000원 10%, 50,000~100,000원 11%, 100,000원 이상 12%). A 가 어느 구간에도 없으면 건너뛴다.
   **상품 금액 상한**을 두면 (예: 300,000원) A 가 그 금액을 넘는 상품은 B 도 읽지 않고 바로 건너뛴다. 비워두면 제한 없음.
6. 구매 입찰 탭에서 희망가 **B**, 마감기한 **7일**, 구매 입찰 계속.
7. 배송방법 **창고 보관** (선택 확인이 안 되면 절대 진행하지 않음), 포인트 있으면 최대 사용, 결제 카드는 그대로.
8. 입찰하기 → 확인 항목 3개 체크 → 입찰하기 → "구매 입찰이 완료되었습니다" 확인 → 탭 닫기.

4 에서 "즉시 구매 / 구매 입찰" 을 누르면 같은 디자인의 다른 모델번호 상품이 있는 상품(의류 등, 2026-09-05 바람막이 실측)에서는
**"모델번호를 확인하셨나요?"** 확인창이 먼저 뜬다. 프로그램은 [확인 후 계속] 을 눌러 넘어간다. 그래도 구매 페이지로 넘어가지 않으면
그 상품(옵션)은 "건너뜀 - 구매 페이지로 넘어가지 않음" 으로 남기고 `dumps/` 에 화면을 남긴다.

**입찰 기준(금액 구간별 마진율, 상품 금액 상한)은 GUI 의 [입찰 기준] 표에서 바꾼다** - `data/bid_rules.json` 에 저장되고
명령행 실행도 같은 파일을 읽는다. 파일이 없으면 `.env` 의 `MIN_MARGIN_RATE` 하나로 된 구간 하나(상한 없음)를 쓴다.
나머지 숫자(30일 / 15건 / 7일 / 상품 수)는 `.env` 에서 바꾼다.

건너뛰는 경우: **마이페이지 > 구매 내역 > 구매 입찰 탭에 지금 입찰 중인 상품** (실행 시작 때 목록을 읽는다. 목록 API 에 상품 ID 가 없어서
`data/bids.json` 기록과 상품명·희망가가 같으면 그 ID 를 쓰고, 없는 입찰만 상세를 열어 API 응답으로 읽는다 - 하나에 1~2초.
그래도 상품 ID 를 못 읽은 입찰은 상품 페이지 제목과 상품명이 같으면 건너뛴다),
체결 거래 표가 없는 상품(아직 리셀 거래가 열리지 않음 - 매 실행마다 다시 확인한다), 빠른배송 판매자가 없는 상품.
**이미 입찰 중인 것만 건너뛰고 그 밖의 상품은 전부 기준에 따라 다시 판정한다** - 예전에 입찰했다가 체결·만료로 목록에서 사라진 상품도
조건이 맞으면 다시 입찰한다. 입찰을 시도하다가 화면이 예상과 달라 못 넣으면(창고보관 선택 확인 실패, 확인 모달 없음 등)
그 상품만 "건너뜀 - 입찰 못 함: 사유" 로 남기고 다음 상품으로 간다.

**옵션이 있는 상품** (2026-09-05 실측, 신발 "(W) 나이키 토탈 90" 기준. 의류 등 다른 랭킹도 옵션이 있으면 같다):

1. "거래 내역 더보기" 패널 위의 옵션 선택 버튼(처음엔 `모든 옵션`)을 눌러 옵션 목록(W220 … W290, S/M/L 등)을 읽는다.
   `모든 옵션` 을 빼고 **화면 순서대로** 옵션을 하나씩 골라 그 옵션만의 체결 표에서 30일 빠른배송 건수를 센다 (페이지 이동 없이 옵션당 1초쯤).
2. 거래량이 기준을 넘는 옵션만 **구매하기 모달에서 그 옵션을 고르고** 나머지는 ONE SIZE 상품과 똑같이 진행한다
   (빠른배송가 A → 일반배송 → 구매 페이지 `/buy/상품ID?size=옵션값` 에서 즉시 판매가 B → 마진 → 입찰. 입찰 화면의 "W240 / 창고보관" 표기까지 확인).
   옵션마다 입찰이 하나씩 들어가며, 한 옵션을 입찰한 뒤 상품 페이지로 돌아와 다음 옵션을 본다.
3. 보고서에는 **옵션마다 한 줄** (옵션 열). 마이페이지에 이미 그 옵션으로 입찰 중이면 그 옵션만 건너뛰고 다른 옵션은 본다.
4. 구매 페이지 주소의 `size` 값(예 `240`)은 화면 표기(`W240`)와 다르다. 프로그램은 모달을 거쳐 도착한 주소에서 값을 읽어
   `data/bids.json` 에 옵션 표기·값을 같이 남긴다 (키 `상품ID:size값`). 점검용으로 `--option W240 W250` 처럼 볼 옵션을 정할 수 있다.

속도: 이미지/동영상/폰트를 받지 않는다(`.env` `BLOCK_IMAGES=0` 으로 끌 수 있다). 상품 하나에 약 6초 (2026-09-04 실측: 페이지 열기 → 체결 내역 3초, A·B 읽기 3초).

**검색으로 상품 고르기** (2026-09-06 실측, `src/kream_reresell/search.py`):

1. 검색 결과 상품 탭(`/search?keyword=검색어`)에 나온 순서(추천순)대로 상품을 하나씩 본다. 순위는 없고 나온 순서가 보고서의 `순위` 열이 된다
   (`랭킹` 열은 `검색:검색어`). 카드는 50개씩 그려지고 스크롤하면 다음 50개가 이어 붙는다 (무한 스크롤).
2. **시도할 상품 수**는 입찰 성공 수가 아니라 검색 결과 앞에서부터 판정해 볼 상품 수다 (검색어마다). 결과가 그보다 적으면 있는 만큼만 본다.
3. 기본으로 검색 결과에 사이트의 **빠른배송 필터**(`delivery_method=quick_delivery`)를 걸어 지금 빠른배송 판매자가 있는 상품만 본다
   (롱샴: 1,276개 → 45개). 판매자가 없는 상품은 A 를 못 읽어 어차피 건너뛰므로, 그런 상품에 상품 페이지·체결 내역 요청(스로틀 대상)을
   쓰지 않으려는 것이다. GUI 의 체크를 풀거나 `.env` `SEARCH_QUICK_ONLY=0` / `--no-quick-filter` 로 끌 수 있다.
4. 검색어를 여러 개 주면(GUI 는 쉼표로 구분) 준 순서대로 검색어마다 위를 반복하고, 결과는 엑셀 보고서 하나에 모인다.
   이미 입찰 중인 상품 건너뛰기, 옵션 상품 처리, 판정·입찰·스로틀 대응은 랭킹과 똑같다 (같은 pipeline).
5. 카드에 적힌 **전체 거래 수**("거래 2,877", 없으면 0건)가 기준(15건)보다 적은 상품은 상품 페이지를 열지 않고 바로 건너뛴다
   (전체 거래 ≥ 30일 빠른배송 건수라 판정이 달라지지 않는다). 시도한 상품 수에는 들고 보고서에 "카드의 전체 거래 N건 < 15건" 으로 남는다.
   랭킹 카드의 "거래 4.1만" 에도 같은 규칙을 쓴다 (`--force` 면 안 쓴다).

**SHOP 카테고리로 상품 고르기** (2026-09-06 실측, `src/kream_reresell/shop.py`):

1. 사이트 상단 HOME / STYLE / **SHOP** 의 카테고리 탭(전체는 뺀 19개: 럭셔리, 트레이딩 카드, 신발, 상의, 아우터, 하의, 가방, 지갑,
   시계, 패션잡화, 컬렉터블, 티켓, 금/은, 뷰티, 테크, 가전, 캠핑, 가구/리빙, 푸드)을 랭킹처럼 골라 그 목록에 **나온 순서(추천순)대로**
   상품을 하나씩 본다. 주소는 검색과 같은 `/search?tab=번호` (신발 44, 가방 63 ...) 이고 카드·무한 스크롤도 검색과 같다.
   보고서의 `랭킹` 열은 `SHOP:신발`, `순위` 열은 나온 순서.
2. 목록에는 빠른배송이 없는 상품도 섞여 있다. **빠른배송 가능한 상품만 입찰**하므로 검색과 같은 **빠른배송 필터**
   (`&delivery_method=quick_delivery`)를 기본으로 걸어 지금 빠른배송 판매자가 있는 상품만 본다 (GUI 체크 해제 / `.env` `SHOP_QUICK_ONLY=0` /
   `--no-quick-filter` 로 끌 수 있다 - 끄면 빠른배송 판매자가 없는 상품은 A 를 못 읽어 "건너뜀" 이 된다).
3. **시도할 상품 수**는 카테고리마다 목록 앞에서부터 판정해 볼 상품 수다 (검색과 같음). 카테고리를 여러 개 체크하면 나열된(탭) 순서대로
   돌고 결과는 엑셀 보고서 하나에 모인다. 카드의 전체 거래 수가 기준 미달인 상품 건너뛰기, 이미 입찰 중인 상품 건너뛰기, 옵션 상품 처리,
   판정·입찰·스로틀 대응은 랭킹·검색과 똑같다 (같은 pipeline).
4. 탭 번호가 바뀌어 다른 카테고리가 열리면 탭을 글자로 찾아 눌러 맞추고 새 번호를 기억한다 (랭킹 칩과 같은 방식).
   명령행: `python scripts/run.py --shop 신발 가방 --limit 30 --dry-run`, `--all-shop`, `--list-shop`.

## 사이트 차단(스로틀) 대응

체결 내역이 안 불러와지는 것(패널이 빈 채 → '불러오는 중 문제가 생겼어요')은 사이트 장애가 아니라 **IP 단위 스로틀**이다 (2026-09-05 실측).
막히면 `api.kream.co.kr/api/p/products/{상품ID}/sales|asks|bids|chart` 요청만 10초 동안 응답 없이 홀드되다 끊기고, 상품 페이지와 다른 API 는
그 순간에도 정상이다. 브라우저에서 쿠키·로그인 토큰·기기 ID 를 다 빼고 보내도 똑같이 막히므로 계정이 아니라 IP(또는 브라우저) 기준으로 보인다
(다른 IP 에선 잘 나온다).
429 나 Retry-After 같은 힌트는 없다. 패널을 열면 이 네 API 가 두 번씩(8건), 옵션을 하나 고를 때마다 네 개(4건)가 나간다 (구매하기 모달·구매 페이지는
이 API 를 안 부른다). 옵션 상품을 0.6초 간격으로 옵션마다 읽던 [입찰] 실행이 상품 13개·옵션 87개(6.5분, 약 450건 = 분당 70건) 만에 막혔고,
막힌 뒤에도 상품마다 두드리면 20분 넘게 안 풀렸다. [재입찰] 의 5분 주기 27건 빠른 확인(구매 페이지만)은 3시간 동안 괜찮았다.

그래서 요청 자체를 줄인다 (`src/kream_reresell/pacing.py`, 사용자 결정 2026-09-05):

1. **안 보는 요청 차단**: 패널을 열면 사이트가 sales 와 함께 asks·bids·chart 도 부르는데 프로그램은 체결 표(sales)만 보므로
   나머지 셋은 서버에 보내지 않고 브라우저에서 빈 목록(200)으로 채운다 (요청을 그냥 끊으면 사이트가 '불러오는 중 문제' 오류로 바꾼다).
   `.env` `TRIM_API=0` 으로 끌 수 있다. 호출이 1/4 로 준다 (옵션 7개 상품: 36건 → 9건).
2. **사람 속도의 간격**: 옵션을 바꾸기 전 2~3.5초, 상품 사이 3~6초를 무작위로 쉰다 ([재입찰]은 원래 입찰 사이 2~4초).
3. **요청 예산**: 스로틀 대상 API 로 나간 요청을 세서 **10분에 `API_BUDGET_PER_10MIN`건**(기본 60)을 넘기면 자리가 날 때까지 쉰다.
   처음 막힌 실행은 분당 70건이었지만 한 번 막혔다 풀린 뒤에는 10분에 110건쯤(분당 11건)으로 또 막혀서, 그 절반으로 잡았다
   (GUI 상태창에 "요청 예산 소진 - N초 쉬는 중"). 0 이면 세지 않는다. 그래도 막히면 기존대로 3건 연달아 판단 불가에서 멈춰 5분마다 확인한다.

4. **모든 옵션 표 먼저**: 옵션 상품은 옵션을 하나씩 고르기 전에 패널의 '모든 옵션' 표(첫 페이지는 패널을 열 때 이미 와 있어 공짜)를
   읽는다. 거기서 기준(15건)을 채운 옵션과, 표가 30일 끝(또는 표 끝)까지 가서 정확히 센 옵션은 고르지 않는다. 표를 한 페이지(50행 = 요청 1건)
   더 넘기는 것은 지금까지 본 거래 속도로 어림한 '30일 끝까지 남은 페이지 수' 가 아직 안 정해진 옵션 수 이하일 때만 한다
   (그래서 하나씩 고르는 것보다 요청이 많아지지 않는다). 거래가 적은 상품은 옵션을 하나도 고르지 않는다 (2026-09-05 실측: 옵션 8개 상품 하나가 40건 → 4건, 거래 많은 옵션 7개 상품 36건 → 8건).
   스로틀 중에 표가 '체결된 거래가 아직 없습니다' 로 그려지는 경우가 있어, 페이지 머리의 거래 수가 0 이 아닌데 표가 비면 0건이 아니라
   판단 불가로 본다 (0건으로 세면 [재입찰]이 입찰을 지운다).

IP 를 바꾸는 우회는 하지 않는다 - 같은 패턴이면 새 IP 도 곧 걸리고 계정까지 묶일 수 있다. 막혔는지는 크롬에서 상품 페이지의
'거래 내역 더보기' 를 눌러 표가 그려지는지로 본다 (curl 같은 브라우저 밖 요청은 막히지 않았을 때도 10초 뒤 500 이라 기준이 안 된다).

## 입찰취소 규칙

마이페이지 > 구매 내역 > **구매 입찰** 탭(`/my/buying?tab=bidding`)에 살아 있는 입찰을 화면 순서대로 본다.

1. 입찰 상세(`/my/buying/입찰번호`)에서 상품 ID · 희망가 · 마감 · 옵션을 읽는다 (`api/m/bids/입찰번호` 응답,
   옵션 상품은 `product_option.key` 가 구매 페이지 주소의 size 값).
2. 그 상품(옵션 상품은 **그 옵션**)을 **다시 처음부터 입찰한다고 생각하고** 위 판단 규칙 2~5 를 똑같이 적용한다
   (최근 30일 빠른배송 건수, A, B, `A - B > A × 구간별 최소 마진율`). 거래량이 모자라도 A/B 까지 읽어 보고서에 남긴다.
   상품 금액 상한은 새로 입찰할 때만 쓰는 규칙이라 이미 넣은 입찰을 다시 판정할 때는 쓰지 않는다.
3. 기준에 못 미치면 상세 화면의 **입찰 지우기** → 확인창 [입찰 지우기]. `DELETE api/m/bids/입찰번호` 가 204 로 끝나야 지운 것으로 본다.
   다 끝난 뒤 목록을 다시 읽어 정말 사라졌는지 확인하고, 남아 있으면 "확인필요" 로 표시한다.
4. 조건을 충족하면 그대로 둔다(입찰유지). 판단할 수 없으면(상품 페이지 오류, 빠른배송 가격을 못 읽음 등) **지우지 않고** "확인필요".
5. 지운 상품은 `data/bids.json` 에서도 빼서, 나중에 조건이 다시 맞으면 새로 입찰할 수 있게 한다.

희망가는 최소 2만원, 천원 단위 (2026-09-04 실측). 취소 전용 조건은 따로 없고 입찰 기준(`data/bid_rules.json`, `.env`)을 그대로 쓴다.

## 재입찰 규칙 ([재입찰])

내가 넣은 구매 입찰보다 누가 더 비싸게 입찰하면 내 순위가 밀린다. [재입찰]은 마이페이지 > 구매 내역 > **구매 입찰** 목록을
화면 순서대로 돌며 밀린 입찰의 희망가를 올리고, **[중지]를 누를 때까지 그 사이클을 반복**한다.

1. 목록의 입찰마다 상품 ID 를 알아낸다 (`data/bid_products.json` 캐시 → `data/bids.json` 기록 → 상세 API 응답.
   한 번 읽은 입찰번호→상품 ID·옵션 값은 캐시 파일에 남겨 다음 실행에도 상세를 다시 열지 않는다. 옵션 상품은 구매 페이지 주소의
   size 값도 알아야 해서 그 값을 모르면 상세를 연다). 탭 하나를 실행 내내 다시 쓴다 (입찰마다 열고 닫지 않음).
2. 상품 페이지 → 구매하기 모달에서 **최신 A(빠른배송 가격)** → 구매 페이지 `/buy/상품ID?size=ONE+SIZE` (옵션 상품은 `size=옵션값`, 예 `240`) 에서
   **최신 B(즉시 판매가)**(지금 가장 높은 구매 입찰가)를 읽어 `A − B > A × 구간별 최소 마진율` 을 판정한다 (7초쯤).
   **밀리지 않은 입찰도 A 가 내려가 마진이 줄었을 수 있으므로 매번 A 를 다시 본다** (2026-09-06 사용자 결정). 거래량은 여기서 보지 않으므로
   상품 페이지의 sales 요청을 빈 응답으로 채워 스로틀 대상 요청은 0건이다.
   B 가 내 희망가 이하이면 밀리지 않은 것: 마진이 기준을 충족하면 **순위유지**(사유에 A·마진율을 남김), **기준 미달이면 그 입찰을 지운다**
   (**입찰취소**, dry-run 이면 **취소대상**, 방식은 아래 3 과 같다).
   **구매 페이지는 떴는데 즉시 판매가가 없으면 그 입찰을 지운다** (**입찰취소**, dry-run 이면 **취소대상**. 2026-09-05 사용자 결정) -
   지우기 전에 상세 API 로 살아 있는 입찰인지 보고 이미 체결·삭제된 입찰이면 **건너뜀**. 지우지 못하면 **확인필요**.
   **구매하기 모달에 빠른배송이 없거나(일반배송만 그려짐) 빠른배송 가격이 없으면 = 지금 빠른배송 판매자가 없으면 그 입찰도 지운다**
   (**입찰취소**, dry-run 이면 **취소대상**. 2026-09-06 사용자 결정 - 빠른배송으로 팔 수 없는 상품의 입찰은 둘 이유가 없음). 모달이 그려진 뒤 본 것이라
   사이트 문제와 다르므로 체결 내역 확인 없이 지우고, 아래 6 의 '연달아 난 수' 에도 넣지 않는다 (스냅샷 `시각_rebid입찰번호_no_fast`).
   상품 페이지가 안 뜨는 등 그 밖의 이유로 A 를 못 읽으면 판단 불가(**확인필요**).
3. B 가 내 희망가보다 높으면(밀림) 마진 미달이면 바로 지우고, 충족하면 상품 페이지를 다시 열어 **처음 입찰할 때와 똑같이** 거래량까지 판정한다
   (최근 30일 빠른배송 건수, 옵션 상품은 그 옵션의 거래량).
   금액이 그사이 바뀌었을 수 있으므로 항상 상품 페이지의 최신 값을 쓴다.
   **기준에 못 미쳐 올릴 수 없으면 그 입찰을 지운다** (**입찰취소**, dry-run 이면 **취소대상**) - 방식과 안전장치는 [입찰취소]와 같다
   (상세의 입찰 지우기 → 확인창 → `DELETE` 204 확인, `data/bids.json` 에서도 뺌). 판단할 수 없으면(상품 페이지 오류 등) 지우지 않고 **확인필요**.
   상품 금액 상한은 [입찰취소]와 마찬가지로 지우는 기준에 쓰지 않는다. 기준은 충족하는데 A 가 상한을 넘기만 하면
   새 입찰 규칙상 올리지도 않고 지우지도 않는다 (**변경안함**).
4. 조건이 맞으면 입찰 상세의 **[입찰 변경하기]** 가 여는 화면
   (`/buy/상품ID?size=옵션값&bid=입찰번호&from=changeBidding&type=bid&price=기존가`, 2026-09-04 실측)에서 처음 입찰과 같은 순서로 채운다
   (옵션 상품은 화면의 옵션 표기가 내 입찰의 옵션과 같은지 확인한 뒤):
   희망가 **최신 B**, 마감 **7일**, 구매 입찰 계속 → **창고 보관**(확인 안 되면 진행 안 함) → 포인트 최대 사용 → 입찰하기 → 확인 3항목 → 입찰하기.
   새 입찰을 하나 더 넣는 것이 아니라 **기존 입찰의 희망가를 바꾸는 것**이라 입찰이 두 개가 되지 않는다. 끝나면 `data/bids.json` 의 가격도 새 희망가로 바꾼다.
5. 목록 끝까지 가면 한 사이클. **몇 사이클 돌지**는 GUI 의 "재입찰 횟수" 칸(`.env` `REBID_CYCLES`, 기본 1회, 0 이면 [중지]까지 계속 / 명령행 `--cycles`, `--once`)으로 정하고,
   **사이클 시작 간격**(GUI 의 "사이클 시작 간격", `.env` `REBID_INTERVAL_MIN`, 기본 5분, 최소 1분)을 지켜 다음 사이클을 시작하고,
   입찰 사이에도 2~4초 무작위로 쉰다. 간격은 **한 바퀴 시작부터 다음 바퀴 시작까지**라서 쉬는 시간 = 간격 − 이번 사이클에 걸린 시간이다
   (예: 32건에 209초 걸리면 91초 쉬고 시작). 사이클이 간격보다 오래 걸리면 30초만 쉬고 바로 다음 사이클로 간다. 목록을 3번 연달아 못 읽으면 멈춘다.
6. **사이트가 응답을 안 줄 때**: 상품 페이지는 뜨는데 구매 페이지의 '즉시 판매가' 나 체결 내역 패널의 행처럼 API 로 채우는 부분만 비는
   시간대가 있다 (2026-09-05 실측: 계속 두드리는 동안 20분 넘게 이어졌고, 7분쯤 쉬니 풀렸다). 상품 페이지 쪽이 비어 판단할 수 없는 입찰은
   **확인필요**(판단 불가)로 남기고 지우지 않는다. 구매 페이지에 와 있는데 즉시 판매가만 없으면 위 2 대로 그 입찰을 지운다 (한 건에 10초쯤).
   판단 불가·오류·즉시 판매가 없음이 **3건 연달아** 나면 최대 10분 쉬되 **5분마다** 구매 페이지를 한 번 열어 보고, 풀렸으면 로그인 상태를 확인한 뒤 바로 이어서 본다
   (사이트가 응답을 안 줘서 즉시 판매가가 비는 동안 입찰이 줄줄이 지워지지 않게 하는 장치). 같은 사이클에서 또 3건 연달아 나면 사이클을 끊고
   다음 사이클 전에 10분 더 쉰다. 판단 불가·즉시 판매가 없음으로 끝난 입찰은 `dumps/` 에 화면 스냅샷(`시각_rebid입찰번호_skip|no_b.png/.txt`)을 남긴다.
   구매 페이지가 로그인 화면으로 넘어가면(로그인이 풀림) 다시 로그인하고 그 입찰을 한 번 더 본다. 목록 페이지가 로그인 화면으로 넘어가도
   (로그인 화면 주소에 `tab=bidding` 이 남아 0건으로 읽히던 문제) 다시 로그인하고 목록을 다시 읽는다. 목록을 못 읽으면 2분 뒤 다시 읽고, 3번 연달아 못 읽으면 멈춘다.
   사이트 차단 기준은 공개돼 있지 않다 - 68건 기준 한 사이클에 8분쯤(입찰 하나 7초 = 상품 페이지·모달·구매 페이지, 쉬는 시간 2~4초, 밀린 것은 +5초) 걸리므로
   5분 간격이면 쉬지 않고 30초만 쉬고 다음 사이클로 간다. 밀리지 않은 입찰은 스로틀 대상 요청이 0건이라 사이클이 길어도 예산은 쓰지 않으며, 이 속도(분당 10~12 페이지)로 [입찰]을 돌렸을 때 막힌 적은 없다 (2026-09-04 기준). 더 빠르게 하고 싶으면 간격을 줄이되 1분 아래로는 내려가지 않는다.

보고서는 `KREAM 재입찰결과 YYYY-MM-DD HHMM.xlsx` 하나에 **사이클이 끝날 때마다 덮어써서** 프로그램이 중간에 죽어도 그때까지의 결과가 남는다
(엑셀로 열어 둔 상태면 시각을 붙인 다른 이름으로 저장). 랭킹 열이 몇 회차인지, 입찰가 열이 처리 뒤 내 희망가.
판정은 변경완료 / 변경대상(dry-run) / 순위유지 / 입찰취소 / 취소대상(dry-run) / 변경안함(상한만 넘음) / 변경못함(희망가·옵션을 못 읽음) / 확인필요 / 오류.
밀렸고 기준도 충족하는데 [입찰 변경하기] 화면이 예상과 달라(상품명·옵션 불일치 등) 못 올린 입찰은 변경 화면을 다시 열어 한 번 더 시도하고,
그래도 못 올리면 그대로 두지 않고 지운다 (입찰취소, 2026-09-06). 상품명·옵션은 '즉시 판매가' 보다 늦게 그려져 최대 12초 기다린 뒤 대조한다
(2026-09-05~06 의 변경못함 3건은 모두 화면이 늦게 그려진 오탐이었다). 사이클 끝 로그에 그 사이클의 스로틀 대상 API 요청 수가 나온다.

## 설치

```
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
copy .env.example .env
```

브라우저는 설치된 크롬을 그대로 쓴다 (`auth/chrome_profile_kream` 프로필). headless 는 봇 탐지에 걸리기 쉬워 쓰지 않고,
대신 크롬 창을 모니터 바깥으로 옮겨 둔 채 실행한다 (작업표시줄에만 크롬 아이콘이 남고, 다른 작업을 방해하지 않는다).
창을 보며 확인하려면 `--show-chrome` 또는 `.env` 의 `SHOW_CHROME=1`, GUI 에서는 [크롬 창 보기] 체크 (실행 중에도 바꿀 수 있다).
로그인은 프로필에 유지되고, 세션이 끊기면 `.env` 의 `KREAM_ID`/`KREAM_PW` 로 이메일 자동 재로그인한다
(`/login/email` 폼, 캡차 없음 - 2026-09-03 확인). 비밀번호를 비워두거나 자동 로그인이 실패하면 크롬 창을 화면으로
불러와 직접 로그인할 때까지 5분 기다리고, 로그인되면 다시 치운다.

```
.venv\Scripts\python scripts\run.py --list-categories                    # 랭킹 이름 목록
.venv\Scripts\python scripts\run.py --search 롱샴 --limit 20 --dry-run     # 랭킹 대신 검색 결과 순서대로 20개 판단 (빠른배송 필터)
.venv\Scripts\python scripts\run.py --search 롱샴 "메종 마르지엘라 지갑"    # 검색어 여러 개를 준 순서대로, 실제 입찰
.venv\Scripts\python scripts\run.py --shop 신발 가방 --limit 30 --dry-run  # SHOP 카테고리 목록을 나온 순서대로 30개씩 판단 (빠른배송 필터)
.venv\Scripts\python scripts\run.py --all-shop --dry-run                  # SHOP 의 모든 카테고리(전체 제외)를 탭 순서대로
.venv\Scripts\python scripts\run.py --list-shop                           # SHOP 카테고리 이름 목록
.venv\Scripts\python scripts\run.py --product 385408 --force --stop-before-submit --inspect
```

- `--category 이름 [이름 ...]` : 랭킹. 여러 개면 준 순서대로 하나씩 랭킹을 열어 처리한다. `--limit` 은 랭킹마다 적용.
- `--all-categories` : 랭킹 탭의 랭킹 21개를 칩 순서대로 전부 돈다.
- `--search 검색어 [검색어 ...]` : 랭킹 대신 검색 결과를 나온 순서대로 본다 (위 "검색으로 상품 고르기"). `--limit` 은 검색어마다 시도할 상품 수.
- `--shop 카테고리 [카테고리 ...]` : 랭킹 대신 SHOP 탭의 카테고리 목록을 나온 순서대로 본다 (위 "SHOP 카테고리로 상품 고르기"). `--limit` 은 카테고리마다 시도할 상품 수.
- `--all-shop` : SHOP 의 카테고리 19개(전체 제외)를 탭 순서대로 전부 돈다.
- `--no-quick-filter` : 검색 결과·SHOP 목록에 빠른배송 필터를 걸지 않는다 (기본은 빠른배송 판매자가 있는 상품만).
- `--dry-run` : 거래량/마진 판단까지만 하고 입찰 폼은 건드리지 않는다.
- `--stop-before-submit` : 입찰 화면을 다 채우되 마지막 "입찰하기" 는 누르지 않는다.
- `--force` : 거래량/마진 조건을 무시한다 (화면 점검용).
- `--inspect` : 화면마다 `dumps/` 에 스크린샷 + 접근성 트리를 남긴다.
- `--product ID ...` : 랭킹 대신 지정한 상품만 본다.
- `--option 표기 ...` : 옵션(사이즈) 상품에서 이 옵션들만 본다 (화면 표기 그대로: `W240`, `M`). 점검용, 비우면 옵션 전부.

## 판매 내역 정리 규칙 ([내역])

달을 고르면 **보관 판매 > 종료** 의 판매 중 **보관 상세의 "거래일시"** 가 그 달인 것을 모아, 건마다 **구매 내역 > 종료** 에서
매입 건을 찾아 짝짓고 정산 시트 모양의 엑셀로 저장한다 (`바탕화면\KREAM 내역 YYYY-MM.xlsx`, 같은 파일이 열려 있으면 시각을 붙여 저장).

화면을 하나씩 열지 않고 그 화면이 부르는 API 를 페이지 안에서 그대로 불러 읽는다 (2026-09-04 실측, 판매 47건에 10초쯤).

- 보관 판매(`api/seller/inventory/items/finished?status=payout_completed`): 보관번호 `id`, 보관판매 주문번호 `oid`(I-SW…),
  판매가, 정산금액(`price_breakdown.total_payout`), **거래일시(`transaction.date_created` = 보관 상세의 거래일시)**, 정산일, 제품코드(`style_code`), 상품명 한/영, 사이즈.
  팔렸지만 아직 정산 전인 것(보관 중 > 판매완료)도 같은 달이면 넣고 `비고` 에 "정산 전" 이라고 적는다.
- 구매 내역(`api/o/bids/?tab=finished`): 결제번호 헤더의 일시(= 주문 화면의 "거래 일시" = **매입 일시**) 와 상품 줄의 입찰번호,
  그리고 **창고보관 링크의 보관번호** (`/my/inventory?…&id=보관번호`). 이 보관번호가 보관 판매의 `id` 와 같아서 매입-판매를 정확히 잇는다.
- 짝이 된 구매의 상세(`api/m/bids/입찰번호`)에서 **매입 주문번호 `oid`(B-SW…)** 와 **매입가(`price_breakdown.total_price` = 즉시 구매가 + 수수료 등, 실제 결제금액)** 를 읽는다.
  매입가는 **항상 수수료 포함** (원본 시트의 레고 포드 GT 줄 114,600원 = 111,000 + 수수료 3,600 과 같은 기준, 2026-09-04 확인).

짝 맞추는 순서: ① 보관번호 → ② 창고보관 링크가 없는 구매는 상세의 `keep.ask_id` 로 보관번호 확인 →
③ 그래도 없으면 상품명·사이즈가 같고 판매보다 먼저 결제된 가장 오래된 구매. 끝내 못 찾으면 매입 열을 비우고 노란 줄로 표시한다
(KREAM 에서 사지 않고 [보유 상품 추가] 로 보관에 넣은 상품이 여기에 해당한다).

엑셀 열은 정산 시트와 같다: `# | 매입 주문번호 | 제품코드 | 제품이름 (한/영) | 사이즈 | 매입 일시 | 매입가 | 보관판매 주문번호 | 판매 일시 | 정산가 | 수익 | 메모`
+ 맨 오른쪽 `비고`(정산 상태, 짝 맞춘 방법). 수익 = `정산가 − 매입가`, 메모 = `수익 × 0.3` 수식이고 아래에 합계 줄이 있다. 거래일시 오름차순(1일 → 말일).

## 바탕화면에서 실행

바탕화면의 **`KREAM 리리셀`** 바로가기를 더블클릭하면 창(`scripts/gui.pyw`)이 뜬다.
맨 위 **상품 고르기**에서 **랭킹** / **검색** 을 고르면 그쪽 설정만 보인다 (둘 다 펼치면 창이 모자라서).

- **랭킹**: 랭킹 목록(랭킹 탭의 21개 전부)에서 원하는 것을 체크하고, 랭킹마다 볼 상품 수·모드(실제 실행 / 판단만)를
  고른 뒤 [입찰]. 체크한 랭킹을 나열된 순서(랭킹 칩 순서)대로 하나씩 돌며, 결과는 엑셀 보고서 하나에 모인다
  (`랭킹` 열, 요약 시트에 랭킹별 판정 수). [전체 선택]/[전체 해제] 버튼이 있다.
- **검색**: 검색어 칸(여러 개면 쉼표로 구분)과 **시도할 상품 수**(입찰 성공 수가 아니라 검색 결과 앞에서부터 판정해 볼 상품 수, 검색어마다)를
  넣고 [입찰]. "빠른배송 판매자가 있는 상품만" 체크(기본 켬)는 검색 결과에 사이트의 빠른배송 필터를 거는 것이다 (위 "검색으로 상품 고르기").
  보고서의 `랭킹` 열에는 `검색:검색어`, `순위` 열에는 검색 결과에서의 순서가 들어간다.
신발·의류처럼 옵션(사이즈)이 있는 상품은 옵션마다 따로 판정해 입찰하고 보고서에 옵션마다 한 줄로 나온다 (`옵션` 열).

**[입찰 기준]** 표: 줄마다 `A 부터(원)` / `A 미만(원, 비우면 끝없음)` / `최소 마진율(%)`. [구간 추가]로 줄을 늘리고
(새 줄의 "부터" 는 앞 줄의 "미만" 으로 채워진다) [삭제]로 지운다. 구간이 겹치면 실행하지 않고 알려준다.
아래 `상품 금액 상한: A 가 __원을 넘으면 바로 건너뜀` 에 금액을 넣으면 (예: 300000) 그보다 비싼 상품은 쳐다보지 않는다 (비우면 제한 없음).
[입찰]/[입찰취소]를 누를 때 자동으로 `data/bid_rules.json` 에 저장되고, [기준 저장]만 눌러도 저장된다.
[입찰취소]를 누르면 마이페이지 구매 입찰 목록을 순서대로 다시 판정해 기준 미달 입찰을 지운다
(랭킹·상품 수는 쓰지 않고, 모드가 "판단만" 이면 지우지 않고 "취소대상" 으로만 표시).
[재입찰]을 누르면 구매 입찰 목록을 반복해서 돌며 밀린 입찰의 희망가를 [입찰 변경하기]로 최신 즉시 판매가로 올린다
(위 "재입찰 규칙"). 밀리지 않은 입찰도 최신 A·B 로 마진을 다시 판정한다. 밀렸는데 기준 미달이라 올릴 수 없는 입찰, 밀리지 않았어도 마진이 기준 미달인 입찰, 구매 페이지에 즉시 판매가가 없는 입찰은 지운다. "재입찰 횟수(회)" 칸에 정한 만큼 돌고 끝나며(기본 1회, 0 이면 [중지]를 누를 때까지 계속), "사이클 시작 간격(분)" 칸이 반복 간격이다.
실행 전 확인창에 몇 회 돌지 나오고, 도는 중에도 [중지]로 멈출 수 있다. 상태줄에 "n회차 k/34 상품명",
사이클이 끝나면 "다음 사이클 HH:MM" 또는 "설정한 n회를 모두 돌아 마침" 이 표시된다. 모드가 "판단만" 이면 올리지 않고 "변경대상" 으로만 표시하며 역시 반복한다.
버튼은 한 번에 하나만 돌릴 수 있다 (크롬 프로필 하나를 한 실행만 쓸 수 있어서, [재입찰]이 도는 동안 [입찰]·[내역]은 눌리지 않는다).
[내역]을 누르면 연도·달을 고르는 창이 뜨고(기본은 지난달) [실행] → 확인을 거쳐 그 달의 판매 내역을
`바탕화면\KREAM 내역 YYYY-MM.xlsx` 로 저장한다 (위 "판매 내역 정리 규칙"). 끝나면 [이번 보고서 열기]로 바로 열 수 있다.
크롬은 화면 밖에서 돌아가고 진행 상황은 이 창에만 표시된다. [크롬 창 보기]를 켜면 실행 중에도 크롬 창을 불러올 수 있다
(끄면 다시 치운다). [중지]를 누르면 지금 보는 상품(입찰)까지만 처리하고 멈춘다.
끝나면 결과 요약과 보고서 경로를 알려준다.

랭킹 이름과 `category_filter` 값은 `src/kream_reresell/ranking.py` 의 `CATEGORY_IDS` 에 있다 (2026-09-04 실측).
값이 바뀌어 엉뚱한 랭킹이 열리면 프로그램이 알아채고 칩을 직접 눌러 맞춘다.

## 결과

- **엑셀 보고서**: `바탕화면\KREAM 결과\KREAM 입찰결과 YYYY-MM-DD HHMM.xlsx` - 실행이 끝나면 저장된다 (자동으로 열지 않음, `--open` 을 주면 연다).
  상품마다(옵션 상품은 옵션마다) 랭킹(검색 모드면 `검색:검색어`), 옵션, 판정(입찰완료/입찰대상/건너뜀/중단/오류/확인필요), 사유, 30일 빠른배송 건수, A, B, A−B, 마진율,
  기준마진(그 상품의 A 금액 구간에 적용된 최소 마진율), 입찰가, 링크.
  저장 위치를 바꾸려면 `.env` 에 `REPORT_DIR=경로`.
- 입찰취소 보고서는 `KREAM 입찰취소결과 YYYY-MM-DD HHMM.xlsx`. 순위 열은 구매 입찰 목록에서의 순서,
  판정은 입찰취소 / 취소대상(dry-run) / 입찰유지 / 확인필요 / 오류, 입찰가 열은 그 입찰의 희망가.
- 재입찰 보고서는 `KREAM 재입찰결과 YYYY-MM-DD HHMM.xlsx` (사이클마다 덮어씀). 랭킹 열이 회차, 판정은 변경완료 / 변경대상(dry-run) /
  순위유지 / 입찰취소 / 취소대상(dry-run) / 변경안함 / 변경못함 / 확인필요 / 오류, 입찰가 열은 처리 뒤 내 희망가. 로그는 `logs/rebid_*.log`.
- 판매 내역([내역])은 `바탕화면\KREAM 내역 YYYY-MM.xlsx` (정산 시트 모양, 위 "판매 내역 정리 규칙"). 로그는 `logs/history_*.log` / `logs/gui_*.log`.
- `data/bids.json` : 이 프로그램이 입찰한 상품 기록. **건너뛰기 기준이 아니다** (건너뛰기는 마이페이지 구매 입찰 목록만 본다).
  마이페이지 목록의 입찰을 상품 ID 로 잇는 데 쓰고(상품명·희망가 일치), 입찰취소로 지운 상품은 여기서 빠진다.
- `data/bid_products.json` : [재입찰]이 읽어 둔 입찰번호 → 상품 ID 캐시 (목록에서 사라진 입찰은 자동으로 빠짐). 지워도 다시 만들어진다.
- `data/run_log.csv` : 본 상품마다 거래량 / A / B / 결과 (누적)
- `logs/run_*.log` / `logs/cancel_*.log` / `logs/gui_*.log` : 실행 로그
- 프로그램이 중간에 죽어 보고서가 안 만들어졌으면 `python scripts/report_from_log.py` 로 마지막 실행분을 엑셀로 만든다.
